ChatGPT desktop + Forgejo

Pull request compatibility, rebuilt at the process seam.

The rebranded desktop app still gets pull request data by running an external gh command. That gives us a stable place to adapt Forgejo without changing ChatGPT, Forgejo, or each repository.

Verdict

The current failure has two layers. ChatGPT first turns the SSH transport address into the wrong API host. After we correct that host, stock gh still sends a GitHub GraphQL request that Forgejo cannot answer. The shim must normalize repository identity, then translate the exact commands used by ChatGPT into Forgejo REST calls.

Observed failure

The exact red command

Captured from the Lavender ChatGPT desktop log while the remote working directory was /home/delta/dev/dirtypages on branch main.

ChatGPT-generated command
gh pr list \
  --head main \
  --author @me \
  --state all \
  --json number,url,state,headRefName \
  --repo 127.0.0.1/dirtydishes/dirtypages

Post "https://127.0.0.1/api/graphql": dial tcp 127.0.0.1:443: connect: connection refused

The repository remote is ssh://git@127.0.0.1:2222/dirtydishes/dirtypages.git. That address is valid for local SSH Git transport on Delta. It is not the repository's public web or API identity, which is git.dirtydishes.dev. Direct replay failed three times in 68 to 76 milliseconds, so this is a deterministic identity error, not a timeout or network race.

Confirmed facts

  • The app constructs and runs external gh commands.
  • The generated repository name uses 127.0.0.1.
  • Canonical Forgejo REST calls work with valid credentials.

Inference

ChatGPT derives the explicit --repo value from the Git remote and strips the SSH port. We infer this from the command and remote configuration because the desktop client is closed source.

Design decision

Treat loopback and canonical hosts as aliases for one repository provider. Normalize them before routing, authentication, API selection, and output.

Diagnosis

Two root causes, then contract gaps

Fixing only the first red error would expose the next one. The implementation must preserve the order below.

  1. Repository identity is wrong

    ChatGPT passes the loopback SSH host as --repo. The shim has no alias model that maps 127.0.0.1 or 127.0.0.1:2222 to git.dirtydishes.dev. Allowing the loopback host would still send HTTPS to the wrong place.

  2. Stock gh speaks GitHub GraphQL

    With the canonical host and a valid token, stock gh pr list reaches Forgejo but gets HTTP 405 from /api/graphql. Forgejo exposes the needed PR facts through REST, not the GitHub GraphQL schema expected by gh.

  3. The existing shim does not match build 6720

    It omits fields, ignores --author @me, lacks pagination, drops the checks event field, misses Linux fj credentials, and can delegate unknown Forgejo operations to real GitHub gh.

Not the cause

The shared Delta app-server is one version behind the bundled client, but it only spawns the command. The desktop JavaScript builds the failing gh arguments. A server restart will not repair the PR panel.

Real GitHub baseline

A checksum-verified gh 2.96 against dirtydishes/lyricslab PR 31 returned all 25 keys. It used null for absent merge objects, an empty string for no reviewDecision, and arrays for comments and reviews. With no checks, it exited 1 with empty stdout and no checks reported on stderr. That warning does not stop the PR page from loading.

Proposed design

One deep compatibility module

The Module owns the messy provider differences. Its Interface stays the same one ChatGPT already uses.

Why this seam has leverage: one Adapter fixes every repository opened through the desktop app. The provider details stay local to the module instead of spreading into wrapper scripts, Git configuration, or each project.

Product boundary

git.dirtydishes.dev is a live test fixture, not a built-in service. The Module must work with any user-configured Forgejo host that the execution machine can reach. Host aliases, credentials, API roots, and repository identities stay scoped to that host.

This deepens the existing design rather than replacing it. The first slice does not need a general GraphQL engine, an HTTP proxy, an MCP server, or a resident daemon. Those would add Interfaces and failure modes before we have evidence that they solve a present need.

Implementation plan

Build from the outside in

Each phase ends with a user-visible or safety gate. A phase does not pass because its helper tests pass.

  1. Phase 0

    Freeze the build 6720 contract

    Turn the observed desktop commands and real gh output into failing end-to-end fixtures before changing behavior.

    Build

    • Golden fixtures for the exact auth, pr list, pr view, and pr checks arguments.
    • A seeded PR fixture with body, comments, commits, review requests, and checks.
    • Process-level tests that assert exit code, stdout, and stderr.

    Challenge

    • Keep internal unit tests, but do not let them define compatibility.
    • Restore truthful trace byte counts so later timing claims have evidence.
    Gate: the new tests fail for the known reasons and a real GitHub control still passes through the delegate.
  2. Phase 1

    Repair identity, authentication, and routing

    Make provider selection correct before translating any additional PR fields.

    Build

    • Add a generic host profile with a canonical host, zero or more transport aliases, an API root, and a host-scoped credential identity.
    • Use git.dirtydishes.dev with aliases 127.0.0.1 and 127.0.0.1:2222 as one fixture, never as a default.
    • Let bootstrap register the Forgejo host found in a user's repository, then require explicit allowlisting and host-specific login or credential import.
    • Normalize aliases before allowlist checks, credential lookup, API construction, and URL output.
    • Read the Linux fj credential store.

    Safety

    • Detect the provider before deciding whether a command is supported.
    • Fail closed for unknown Forgejo operations.
    • Never send Forgejo tokens or repositories to GitHub.
    Gate: the original Dirtypages command reaches canonical Forgejo and returns an authoritative empty PR list. A second fixture on an unrelated Forgejo domain discovers, authenticates, and reads its own repository without Dirtydishes configuration. Neither route contacts GitHub.
  3. Phase 2

    Implement the exact read surface

    Translate the commands required to open and keep the native PR screen fresh.

    PR discovery and view

    • Resolve @me from GET /user.
    • Paginate branch and author filtered PR lists.
    • Return all 25 requested fields with matching null, string, object, and array shapes.
    • Fetch body, commits, comments, reviews, requested reviewers, and head SHA.

    Checks and timing

    • Use combined commit status for current state, not raw status history.
    • Add action runs for event, times, links, and workflow names.
    • Match real gh when no checks exist.
    • Apply a five-second deadline to each command.
    Gate: Islandflow PR 36 renders all requested keys, its body, commits, two comments, and checks in an isolated live test.
  4. Phase 3

    Package without disturbing the host

    Install the Adapter where the remote app-server already looks for gh.

    Install

    • Place the wrapper at /home/delta/.local/bin/gh.
    • Use an explicit, checksum-pinned gh 2.96 path for GitHub delegation.
    • Keep the system gh unchanged.

    Prove

    • Confirm the app-server child PATH chooses the wrapper before /usr/bin/gh.
    • Confirm config and credentials remain private.
    • Do not restart active ChatGPT tasks.
    Gate: a fresh child process launched through the existing remote server resolves the wrapper and passes both Forgejo and GitHub smoke tests.
  5. Phase 4

    Validate the native screen

    Use the desktop interface as the final compatibility test.

    Forgejo

    • Dirtypages main reports no matching PR without an unavailable status.
    • Islandflow PR 36 opens with complete header, body, comments, commits, and checks.
    • Polling traces remain within each command deadline.

    GitHub control

    • Lyricslab PR 31 still loads through real gh 2.96.
    • A repository with no checks shows the native nonfatal warning.
    • No Forgejo command appears in GitHub traffic.
    Stop rule: stop after the read screen is complete, truthful, and stable. Plan mutations and optional enrichment as separate work.
Forgejo adapter

REST facts behind the GitHub-shaped output

Live Forgejo 15.0.3 and its OpenAPI schema provide the core read facts. Projection code should mark where a value is exact, derived, or unavailable.

Honesty rule

Forgejo does not expose exact GitHub review-thread reply and resolve semantics. Do not invent them. For a later thread projection, return viewerCanResolve: false and viewerCanUnresolve: false until the action has a proven Forgejo equivalent.

Why Islandflow PR 36 is the main Forgejo fixture
It is open, has a branch name, body, two comments, commits, three statuses, and an action run. That makes it dense enough to expose field omissions without requiring a mutation. The validation should use an isolated worktree so it does not disturb the existing checkout.
Why the no-checks warning is not the same bug
Real GitHub gh pr checks --json exits 1 when a PR has no checks. ChatGPT treats that as a nonfatal warning and still loads the PR page. The Forgejo failure happens earlier in pr list, so the whole PR status becomes unavailable.
Boundaries

Deliberately deferred

These may be useful later. None belongs in the first proof that the native PR screen can work.

Later reads

  • Fixed optional GraphQL enrichment by exact semantic match
  • Global PR board and cross-repository search
  • Review-thread projection where Forgejo has real equivalents

Later writes

  • Comments, reviews, merges, and reviewer changes
  • One observed desktop mutation at a time
  • Separate authorization and rollback for each class

Not planned

  • A general GitHub GraphQL parser
  • An HTTP proxy or MCP layer for the native panel
  • A daemon or cache before measurements require one
